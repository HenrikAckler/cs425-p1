# RFC 5321: SMTP Implementation Notes for CS425 Project 1

This is a focused extract of RFC 5321 for the assignment in
`sourceForAI/assignment.md`. It covers the protocol behavior the client and
its tests must implement. It is not a replacement for the full RFC.

## 1. Wire Format

SMTP is a line-oriented, request/reply protocol over a reliable, ordered byte
stream such as TCP. Commands, replies, and message lines end with **CRLF**:

```text
<CRLF> = "\r\n"
```

The client must not send bare CR or LF characters. A reader must handle both
of these cases:

- one line arriving in several reads;
- several lines arriving in one read.

Keep unread bytes in a receive buffer and read more only when a complete CRLF-
terminated line is not already buffered. A line reader must report a clean
transport error if the peer closes the connection before the requested line is
complete.

SMTP commands are ASCII and are case-insensitive except for mailbox local
parts. The command verb is followed by a space when it has an argument and by
CRLF otherwise.

The RFC minimums relevant to this project are:

- command line, including CRLF: 512 octets;
- reply line, including CRLF: 512 octets;
- text line, including CRLF: 1000 octets;
- local-part of a mailbox: 64 octets;
- domain name: 255 octets;
- path, including punctuation: 256 octets.

The assignment's client should reject address and subject input containing a
bare CR or LF. Otherwise, supplied text could inject an SMTP command or mail
header.

## 2. Replies

Every SMTP command produces exactly one reply. A reply begins with a three-
digit code. The first digit determines the broad result:

| Code class | Meaning | Client behavior |
|---|---|---|
| `2yz` | Positive completion | The requested action completed. |
| `3yz` | Positive intermediate | Send the additional information requested. |
| `4yz` | Temporary failure | The action did not occur; retry may work later. |
| `5yz` | Permanent failure | The request was rejected; do not blindly repeat it. |

The client must decide from the numeric code, not reply text. For this
assignment, a reply is accepted only when its code is the one expected for the
current step. Any other code is a session failure and must be reported with
the actual reply.

### Multiline replies

A reply may contain multiple lines. Every line has the same three-digit code.
Continuation lines have a hyphen immediately after the code; the final line
has a space immediately after the code:

```text
250-smtp.example.com
250-PIPELINING
250 SIZE 10240000
```

The client must read all lines before deciding whether the reply is acceptable.
The reply is complete when the fourth character is a space (or, for tolerant
parsing, when the code is followed by the final-line form). A line with a
hyphen is not a complete reply. The complete reply should be retained so an
error can identify what the server actually sent.

The assignment uses `HELO`, not `EHLO`, so extension negotiation and parsing
an EHLO capability list are unnecessary.

## 3. SMTP Session and Mail Transaction

The server sends a greeting immediately after the TCP connection is opened.
The client must read and validate it before sending any command.

The required assignment sequence is:

```text
S: 220 ...                         # greeting
C: HELO <helo-host>
S: 250 ...
C: MAIL FROM:<from>
S: 250 ...
C: RCPT TO:<to>
S: 250 ...
C: DATA
S: 354 ...
C: <message data, terminated by CRLF . CRLF>
S: 250 ...
C: QUIT
S: 221 ...
```

The client must wait for the complete reply after every command before sending
the next command. It must stop immediately and clean up if a reply is wrong or
the transport fails. It must not send message data unless `DATA` receives a
`354` reply.

### HELO

```text
HELO <domain-or-host><CRLF>
```

The client identifies itself with the configured host name. The assignment
defaults this value to `localhost` and allows `-H` to override it. `HELO` must
be sent before `MAIL`.

### MAIL

```text
MAIL FROM:<reverse-path><CRLF>
```

This begins a transaction and records the envelope sender. There is no space
before the colon in `FROM:`. An empty reverse path is written as `MAIL
FROM:<>`, but the assignment normally supplies a sender address.

### RCPT

```text
RCPT TO:<forward-path><CRLF>
```

This records one envelope recipient. There is no space before the colon in
`TO:`. It follows `MAIL` and precedes `DATA`.

### DATA and end of data

```text
DATA<CRLF>
```

After the server replies `354`, send the message content. The message data is
terminated by the exact sequence:

```text
<CRLF>.<CRLF>
```

The final period is a line containing only a period. Do not add an extra CRLF
between the message's final line and this terminator when the message already
ends in CRLF.

The server accepts responsibility for the message only after it receives the
terminator and returns a positive completion reply, normally `250`. A `4yz` or
`5yz` reply at this point means the client still owns the message and the
session has failed for this assignment.

### QUIT

```text
QUIT<CRLF>
```

The server replies `221` and then closes the connection. The client should send
`QUIT` on a normal successful path and wait for its reply before closing its
socket.

## 4. Message Construction

The envelope commands and message headers are separate concepts. For this
assignment, construct the DATA payload as:

```text
From: <from><CRLF>
To: <to><CRLF>
Subject: <subject><CRLF>
<CRLF>
<dot-stuffed body><CRLF>
.<CRLF>
```

The subject defaults to an empty string. The body comes from `-b` or stdin.
The header blank line separates headers from the body.

### Dot transparency (dot stuffing)

Before sending each body line, inspect its first character. If it is a period,
prepend one additional period:

```text
body line       transmitted line
---------       ---------------
.hello          ..hello
..hello         ...hello
hello           hello
```

The server removes one leading period from every non-terminator data line that
starts with a period. A body line that becomes a single period on the wire
would be mistaken for the end of the message, so it must be doubled.

## 5. Command Ordering and State

The relevant state transitions are:

```text
connected -> greeting received -> HELO accepted ->
MAIL accepted -> at least one RCPT accepted ->
DATA accepted (354) -> data sent -> message accepted (250) ->
QUIT accepted (221)
```

`MAIL` resets any previous transaction buffers. `RCPT` may be repeated for
multiple recipients, though this assignment has one recipient. `DATA` is
invalid before an accepted `MAIL` and at least one accepted `RCPT`.

`RSET` aborts the current transaction and returns the server to its initial
post-HELO state, but the assignment does not require using it. `NOOP`, `VRFY`,
`EXPN`, and `HELP` are unrelated to the required client flow.

## 6. Implementation and Test Implications

The protocol layer should be independent of sockets. Its pure helpers can
implement these operations without I/O:

- parse the three-digit reply code;
- determine whether a reply line is final or a continuation;
- build CRLF-terminated commands;
- dot-stuff body lines;
- build the DATA payload.

The session layer should perform line reads, complete-reply reads, writes, one
command/check operation, and the full sequence through read/write callbacks
plus a context pointer. The socket layer should only adapt `getaddrinfo`,
`connect`, `recv`, and `send` to those callbacks.

Tests should exercise every declared helper and the complete session without a
network. In particular, cover multiline replies, replies split across reads,
multiple replies in one read, a receive buffer that cannot hold a reply, a
mid-session hangup, and each unexpected status code in the required sequence.

## 7. Relevant Reply Codes

These are the codes needed by the assignment and the surrounding RFC rules:

| Code | Meaning |
|---|---|
| `220` | Service ready / connection greeting |
| `221` | Service closing transmission channel |
| `250` | Requested action completed |
| `354` | Start mail input; end with `<CRLF>.<CRLF>` |
| `421` | Service unavailable; closing channel |
| `450` | Mailbox unavailable temporarily |
| `451` | Local processing error |
| `452` | Insufficient storage or too many recipients |
| `500` | Command unrecognized or syntax error |
| `501` | Syntax error in parameters or arguments |
| `502` | Command recognized but not implemented |
| `503` | Bad command sequence |
| `550` | Mailbox unavailable or policy rejection |
| `552` | Storage allocation exceeded |
| `553` | Mailbox name not allowed |
| `554` | Transaction failed / no SMTP service |

The client should be prepared to receive an unlisted three-digit code and
classify it by its first digit, but the assignment's scripted session tests
should compare each step to its required exact code.
